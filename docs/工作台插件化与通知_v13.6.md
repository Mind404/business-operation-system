# 工作台插件化与审批通知 v13.6

日期：2026-11-20
版本：v13.6.0.0

## 一、这版解决什么

v13.5 把冻结、解冻、发布统一进流程引擎后，工作台仍保留旧的 WBS 计数看板、旧 `tasks` 表待办和跨插件汇总数字。它带来两个问题：

1. 计数与实际插件数据脱节：顶部数字不是用户真正要处理的清单；
2. 人员关联不统一：同一负责人可能写成账号、姓名或自由文本，导致待办漏人。

v13.6 的处理原则是：**工作台不再做全局计数，只做“按插件分化的处理清单”**。每个插件自己决定展示什么待办、什么通知，平台统一把事项归到「用户管理」里的真实人员。

## 二、工作台新结构

工作台页面从上到下：

1. 欢迎条：显示当前登录人的姓名/账号，不再显示逾期数、项目数等 KPI；
2. 插件通知：按来源插件分组，展示审批驳回等通知，可单条打开或全部标为已读；
3. 插件待办：按插件分组。流程与审批、WBS 计划管理、版本规划管理各自成块；
4. 流程与审批面板：保留待我发起、待我审批、我发起的、运行中/异常四个页签；
5. 常用功能与最近动态（最近动态仅平台管理员可见）。

旧的四张 WBS KPI 卡片、顶部逾期数字、旧 `tasks` 表待办、跨插件“共 N 项未完成”已经下线。数据库里的旧 `tasks` 表不删除，但工作台不再读取。

## 三、插件模块契约

内置/外置插件可以在 `plugins/<id>/routes.py` 暴露：

```python
def workbench_modules(db, user_ctx):
    return [{
        'plugin_id': 'wbs',
        'plugin_name': 'WBS 计划管理',
        'icon': '🗓️',
        'kind': 'todo',          # todo / notice
        'title': '我的任务',
        'items': [...],
    }]
```

`user_ctx` 由平台统一解析：

```json
{
  "id": 1,
  "username": "admin",
  "display_name": "系统管理员",
  "role": "platform_admin",
  "aliases": ["admin", "系统管理员"]
}
```

平台会为每个 item 补 `owner_user_id / owner_username / owner_display_name`，插件也可以自己覆盖。旧契约 `my_todos(db, username)` 继续兼容。

每个 item 统一使用：`title / url / status / due / days_left / level`。其中 `level` 取 `overdue / soon / near / later / none`，用于插件块内的筛选，不参与任何全局汇总。

当前接入：

- 流程与审批：待审批任务，按当前用户 ID + 角色取；
- WBS 计划管理：负责人为当前用户账号或姓名的未完成任务；
- 版本规划管理：当前用户负责的产品下，规划中待冻结、已冻结/开发中待提测、测试中发布清单未齐或待发布的版本节点。

插件停用后，工作台不再渲染它的模块。单个插件抛错只跳过该插件，不影响其他模块。

## 四、人员关联

- 工作台先按会话 `user_id` 回查 `users` 表；查不到再按账号/姓名回查；
- WBS 待办同时匹配 `owner=账号` 和 `owner=姓名`，兼容存量未规范化数据；
- 版本规划产品负责人改为从「用户管理」选择：
  - 新建产品时，填了负责人但匹配不到用户，直接拒绝；
  - 编辑时，历史未关联文本（如“张工”）可以原样保留，避免破坏存量数据；
  - 新保存的负责人统一存账号，页面显示“姓名（账号）”，未关联的显示“未关联账号”。
- 通知表同时存 `user_id + username + display_name`，以 `user_id` 做权限判断，姓名仅作展示快照。

## 五、审批驳回通知

新增 `wf_notifications`：

| 字段 | 说明 |
|---|---|
| `user_id` | 接收人，用户管理主键 |
| `username/display_name` | 写入时的展示快照 |
| `plugin_id` | 来源插件，用于工作台分组 |
| `event_key` | 来源状态节点 |
| `title/body` | 通知标题与正文 |
| `url` | 打开后跳转地址，仅允许站内 `/` 开头 |
| `instance_id/business_key` | 关联流程实例与业务单号 |
| `read_at` | 已读时间，空串为未读 |

触发规则：

- 流程最终 `rejected` 后，无论插件是否注册 `on_reject`，都通知发起人；
- 通知在驳回写回成功后写入；写回失败时实例进 `error`，不提前发“已驳回”通知；
- 同一实例 + 同一用户 + 同一事件只保留一条，唯一索引兜住并发；
- 工作台按 `plugin_id` 分组展示；打开通知后标为已读并跳转流程实例；
- 可“全部标为已读”，只影响当前登录人。

## 六、事件流水保留期

按已确认方案执行：

- `wf_event_log` 默认保留 **180 天**；
- 总量最多 **50 万条**；
- 先删超过 180 天的行；若仍超量，再按 id 从旧到新删除多余行；
- 进程内每个自然日最多执行一次，启动建表/首次审批初始化时触发；
- 只清理流水，不动物业业务数据、流程实例和审批记录。

## 七、边界与未做项

- CSRF 防护按用户决定暂不做；
- 审批入口仍统一在工作台，不恢复 WBS 业务页的本地审批入口；
- 解冻权限仍只给管理员/平台管理员，产品负责人和版本负责人不能直接解冻；
- 旧 `tasks` 表保留但不再展示，是否物理删除留到后续数据治理；
- 历史产品负责人若不是系统用户，会显示“未关联账号”，不会自动猜测映射；
- 通知默认保留，不跟随事件流水清理；后续如需通知保留期可单独加策略。
