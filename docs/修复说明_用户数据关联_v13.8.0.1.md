# v13.8.0.1 修复说明：数据恢复必须恢复“用户—业务关联”

日期：2026-11-21  
分支：`fix/backup-user-merge`  
基线：v13.8.0.0（`e9430bb`）

## 一、问题不是“少恢复一张 users 表”

v13.8.0.0 的「只恢复数据」把 `users` 当作账号配置跳过，设计假设是“账号属于当前环境，不应该被旧备份覆盖”。这个假设只在系统刚装好、还没有业务数据时成立。

系统运行一段时间后，账号已经和业务数据绑在一起：

- 主库硬关联（数字用户 ID）：`user_plugins.user_id`、`wf_tasks.assignee_id`、`wf_instances.initiator_id`、`wf_events.actor_id`、`wf_notifications.user_id`、`wf_trigger_queue.initiator_id`
- 主库文本关联（用户名/显示名）：WBS 项目/任务的负责人、参与人、审批人；审批实例发起人、任务处理人、事件操作人；通知接收人；操作日志操作人；流程定义/触发创建人；共享表格创建人/更新人
- 版本规划库文本关联：产品负责人、版本冻结人、需求过滤人、检查执行人、发布定稿人、各类日志操作人

只跳过 `users` 会造成两类断档：

1. 备份里有、当前没有的账号完全不回来，业务记录变成“有负责人名字、没有这个人”；
2. 备份和当前的账号 ID 不一致（例如同名账号在不同库里 ID 不同，或备份 ID 与当前另一个账号撞号），恢复后 `assignee_id` 等硬关联会指向错误的人，比“找不到人”更隐蔽。

因此修复目标不是“把 users 整表搬回来”，而是：**账号身份按用户名合并，业务引用按旧 ID→新 ID 重映射，现有账号的密码/角色/状态不回退。**

## 二、修复后的恢复语义

### 1. 非空系统升级恢复（merge）

- 备份里有、当前没有的账号：补进来，保留备份里的密码 hash、显示名、部门、角色、启停/删除状态。
- 当前已有的同名账号：保留当前的密码、角色、启用状态、删除状态，以及已经维护过的显示名/部门；只有当前显示名/部门为空或等于用户名时，才用备份的非空值补齐。
- 只为本次新补的账号补回 `user_plugins` 授权；已有账号的授权保持当前状态。
- 业务表搬完后，对所有搬迁表的 `user_id / assignee_id / initiator_id / actor_id` 做一次旧 ID→新 ID 重映射，使用单条 `CASE` 更新，避免 3→10、10→3 这种交换时互相覆盖。
- 恢复前后各做一次审计：
  - 恢复前看备份自身：业务表里的用户 ID 是否都能在备份 `users` 找到，识别“备份本来就断档”；
  - 恢复后看目标库：还有多少条用户 ID 指向不存在的账号。
- 摘要和操作日志会记录：补回多少账号、保留多少账号、重映射多少条、补回多少插件授权、备份自身/恢复后还有多少孤儿引用。

### 2. 全新系统/换机恢复（full）

当前库被判定为“刚装好还没人用”时，账号随主库整库导入，恢复后要求用备份里的账号重新登录。提示中的账号数量按备份实际账号数显示，不再误用恢复前默认账号数。

### 3. 旧备份没有 `users` 表

不阻断业务数据搬迁；保留当前默认账号，并在恢复结果和操作日志中明确提示“备份中没有账号表，业务里的负责人可能显示为账号名”。

### 4. 插件库恢复

插件库不进入账号合并。但恢复前先按当前代码建好插件表，再搬数据，最后再补一次表/列/迁移。这样空插件库、换机场景不会把备份里的表全部当成“目标库不存在”而跳过。

## 三、举一反三排查到的其他问题

| 场景 | 原行为 | 风险 | 处理 |
|---|---|---|---|
| 备份与当前账号同 ID 不同人 | 直接按 ID 关联 | 待办/审批指向错误的人 | 按用户名合并并重映射 ID |
| 备份自身有孤儿用户 ID | 目标库恰好有同号账号时看起来“正常” | 最隐蔽的错误关联 | 恢复前审计备份并告警 |
| 恢复后仍有孤儿 ID | 无提示 | 页面显示“找不到处理人” | 恢复后审计并写入摘要/日志 |
| 新补账号没有插件授权 | 账号能登录但插件不可用 | 功能断档 | 只对新账号补 `user_plugins` |
| 已有账号资料为空 | 备份里的姓名/部门丢失 | 显示成登录名 | 只补空值，不覆盖已维护资料 |
| 空插件库恢复 | 目标表不存在，备份表被整张跳过 | 恢复后插件页是空库 | 恢复前先建表，恢复后再对齐 |
| 旧备份无 `users` | 空库 full 模式可能在 `bak.users` 上报错 | 恢复中断 | 有账号表才走 full，否则保留默认账号并提示 |

## 五、明确边界

- 不恢复 `user_sessions`：避免把在线用户批量踢下线；已有系统恢复后当前登录保持有效。
- 不恢复 `ai_providers`：旧 API key 可能已失效，避免恢复后 AI 不可用。
- 已有账号的密码、角色、启用状态、授权不会被备份整体回退；这是“升级恢复”和“整库回退”的区别。需要完全回到备份时刻，仍应使用「整库覆盖」。
- 账号身份以**用户名**为准。系统禁止复用已删除账号的登录名，因此同名账号被视为同一人；如果历史上存在手工改库造成的同名不同人，本修复无法自动判别。
- 备份里的已停用/已删除账号会按原状态补回，不会被自动启用。
