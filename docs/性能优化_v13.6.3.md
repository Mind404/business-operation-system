# v13.6.3.0 卡顿排查与性能优化

## 现场现象
- 系统整体卡顿，日志大量 `database is locked`。
- `_bind_login_session`、流程通知幂等索引、事件流水清理均出现写锁失败。
- `/univer/` 首次打开时在建表登记处出现 `database is locked`。

## 根因
1. `plugin_system._main_db()` 在每个请求的新连接上都执行 `PRAGMA journal_mode=WAL`。
   该 PRAGMA 需要独占写锁；waitress 16 线程并发时，所有请求排队抢锁，超时后返回 `database is locked`，表现为页面卡顿、登录写入失败。
2. `workflow_routes` 的 `before_request` 每次进入流程页都调用 `workflow_engine.init_tables()`。
   该函数每次执行通知去重 `DELETE`、唯一索引创建和事件流水清理；通知量大时会长时间持有写锁。
3. 表格插件 `_init_tables()` 在首屏多个请求中并发执行建表/登记。
4. 页面一次性渲染全量数据：1000 条个人待办的工作台约 593KB HTML；1000 条任务的 WBS 详情约 3.3MB HTML，浏览器解析和绘制明显变慢。

## 修复
- 删除每请求 WAL 切换；启动时一次性设置 WAL，连接统一 `busy_timeout=30000`、`timeout=30s`。
- 流程引擎建表/去重/清理改为每库进程内只执行一次；后续请求快速返回。
- 表格插件建表加进程内锁与每库一次性标记；插件登记改为 `INSERT OR IGNORE`。
- 工作台待办统计仍按全量，首屏只渲染前 40 条，并显示总条数和插件入口。
- WBS 详情按每页 100 条分页；`task_highlight` 自动跳到任务所在页；保留自然排序。
- 修复事件流水清理在无 `row_factory` 连接上读取 `row['c']` 的异常。

## 效果
| 页面 | 修复前 | 修复后 |
|---|---|---|
| 工作台（1000 条待办） | 593KB | 70KB |
| WBS 详情（1000 条任务） | 3.3MB | 419KB/页 |
| 20 线程 120 请求 | 多次 database is locked | 0 错误，全部 200 |

## 验证
- v13.2 34/0、v13.3 45/0、v13.4 47/0、v13.5 95/0、v13.6 61/0。
- 60 用户 / 1.2 万 WBS 待办 / 1.8 万通知压测 ALL PASS；工作台 P50=12.5ms、P95=26.0ms。
- 20 线程并发登录 + 首页/WBS/版本/流程/表格：120 请求 0 错误。

## 兼容性
- 数据模型、接口、审批出口不变。
- 工作台待办超过 40 条时只影响首屏展示，完整列表仍在对应插件内。
- WBS 详情超过 100 条时通过分页查看，跨页编辑、导入、导出逻辑不变。
