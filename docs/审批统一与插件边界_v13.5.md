# 审批统一与插件边界（v13.5）

## 一、一句话结论

平台只保留一套“多人审批”：**流程引擎**。插件负责业务校验、业务动作和状态上报，不再自己维护第二套多人审批；管理员/平台管理员自己的操作不走审批。

## 二、哪些迁到了流程引擎，哪些留在插件

| 业务 | 迁移到流程引擎 | 仍留在插件内 | 说明 |
|---|---|---|---|
| WBS 项目立项 | 是 | 项目成员、日期、负责人维护 | 流程通过/驳回后写回 `approval_status` |
| WBS 任务创建 | 是 | 任务拆分、进度、附件、依赖 | 普通用户建任务必须经“负责人确认 + 管理员审批” |
| 版本冻结 | 是 | 必须有需求、需求构成锁定 | 通过后执行 `_apply_freeze` |
| 版本解冻 | 是 | 必须填写解冻原因 | 普通用户可申请，管理员审批后执行 |
| 版本发布 | 是 | 7 项确认清单 | 清单是业务硬门禁，不是审批；签核由流程节点替代 |
| 版本创建/归档/需求过滤/车次转版本 | 否（仅通知） | 业务动作 | 上报事件流水，可绑定知会流程 |

### 判定“已托管”的三个条件

1. 该状态节点存在启用中的绑定；
2. 绑定的流程模板本身启用；
3. 当前流程版本里确实包含该节点的写回动作。

三者同时满足才算托管。只看“有没有绑定”不够，否则会出现“审批通过了但业务状态没变”。

## 三、管理员免审批规则

- 判定：`session['user_role'] in ('platform_admin','admin')`。
- 管理员/平台管理员自己发起冻结、解冻、发布、WBS 立项、WBS 建任务：**直接生效，不创建流程实例，但写事件流水**。
- 管理员不能替普通用户“绕过”审批：普通用户提交的单据仍在流程中心，由管理员审批。
- 管理员在业务页直接点 WBS 本地“通过”会被拒绝，必须去流程中心，避免同一单据两套审批。

## 四、插件接入三步

1. `register_event(..., write_back={key,label,plugin}, on_reject={...})`
   - `write_back`：审批通过后写回业务状态的动作；
   - `on_reject`：流程驳回后写回“已驳回”，避免单据永远停在“待审批”。
2. `register_action(key, handler)`：handler 自己开关插件库连接；不要假设有 Flask 应用上下文；优先使用 `ctx['db']` 主库连接。
3. 业务入口调用 `emit_state_change(..., start_now=True)`
   - 门禁类动作必须 `start_now=True`，表示“不审批就不能落地”；
   - 通知类动作不要 `start_now`，进入待发起队列或直接留痕。

### 插件开发硬约束

- 托管时，插件内的本地“通过/驳回”按钮必须隐藏或拒绝。
- 普通用户在门禁流程未配置/被停用时必须**拒绝操作**，不能回退成“直接生效”。
- 写回动作必须幂等：重复执行不能重复发 Release Note、重复改需求状态。
- 驳回写回必须存在；否则流程驳回后业务单据状态不完整。
- 业务库与平台主库分离，动作中禁止把插件表写进主库。

## 五、事件流水

所有上报都写 `wf_event_log`，未绑定流程也留痕。`mode` 取值：

- `unmatched`：节点未绑定；
- `queue`：进入待发起队列；
- `started`：已创建流程实例；
- `duplicate`：同一业务单号已有未结束实例；
- `skipped`：流程模板被停用。

## 六、升级与默认配置

v13.5 启动时会为所有“注册了写回动作”的门禁节点**自动生成默认审批流程并绑定**，只处理“从未绑定过”的节点；管理员已绑定（包括主动停用）的节点不会被覆盖。

自动生成的流程 Key 为 `auto_<event_key>`，可在流程管理中直接改步骤或换成自定义流程。

## 七、运维注意

- SQLite 备份必须使用平台备份入口（内部使用 SQLite backup API + WAL checkpoint）。直接复制 `.db` 文件会漏掉 WAL 中尚未 checkpoint 的数据。
- 同一业务单号在“运行中/等待/异常”状态只允许一个实例，由部分唯一索引兜底；若老库已有重复实例，索引会降级并打印告警。
- `wf_event_log` 当前不自动清理，数据量随业务上报线性增长，需定期归档（见决策项）。
