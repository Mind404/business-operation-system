## V13.0.0 · 双版本规划插件对照版

平台本体 V13.0.0，内置两套可卸载的「版本规划」外部插件，用于实际体验后决定留哪一套。

### 这个版本包含什么

- **平台主体**：工作台、计划管理（WBS）、需求统计管理、合同台账、用户与权限、导航排序、备份与恢复、AI 数据读取、插件管理。
- **版本规划管理（version_plan，13.0.1.1）**：移植并增强版。需求归集 → 四维评分（价值35 / 客户25 / 紧急20 / 成本反向20）→ 车次日历 → 装车（含改挂、候补、留痕）→ 版本清单 + 三四方签核 → 发布门禁 → Release Note → 客户回告。
- **版本规划·原版风格（version_plan_lt，13.1.0.0）**：与上一套同规则、同数据模型的平行实现，用于对照取舍。当前两套共用平台统一皮肤，尚未做原版 Tailwind 视觉 1:1 还原。

### 两套插件怎么共存

| 维度 | 版本规划管理 | 版本规划·原版风格 |
| --- | --- | --- |
| 插件 id | `version_plan` | `version_plan_lt` |
| 路由前缀 | `/version_plan` | `/version_plan_lt` |
| 数据表前缀 | `version_plan_*` | `version_plan_lt_*` |
| 独立数据库 | `app/data/version_plan.db` | `app/data/version_plan_lt.db` |
| 卸载 | 支持（保留业务数据表） | 支持（保留业务数据表） |

- 两套在插件管理页均可【停用】与【卸载】；停用只隐藏导航并拦截访问，数据不动。
- 卸载会删除该套插件代码目录并保留数据表；误删可用 `app/` 下的插件包重新上传安装。
- 操作其中一套不会改动另一套的数据，也不影响平台其它模块。

## V13.0.0.1 · 修复版（双版本规划插件对照）

在 V13.0.0 基础上修复三个"装到别人电脑上就出问题"的场景。版本号升到 13.0.0.1。

### 修了什么

1. **插件管理页满屏"尚未建表"告警** — 根因：插件建表原本是"第一次打开插件页面才触发"，一旦插件库文件缺失或为空（解压不全、被安全软件清理、旧目录覆盖安装），管理页就会刷出几十条告警，而且不点开插件页就永远不自愈。现在**启动时自动补建全部外部插件表**，并校验告警归零。
2. **导航看不到两套版本规划插件** — 覆盖两种成因：插件库缺失导致注册失败 → 启动自愈自动从内置种子库恢复；插件被停用 → 启动窗口与自检报告直接标出 `启用=否`。
3. **端口被旧实例占用** — 上次没关掉的窗口继续占着 5000 时，新版本自动顺延到 5001…并在窗口里大字提示新地址，避免"看到的是旧系统、以为新版没生效"。
4. **新增 `selfcheck.bat`** — 双击输出插件启用状态、各库文件表数量、一致性告警条数，出问题可直接截图。

### 自愈机制说明

- `app/data/_seed/` 内置两套插件的完整种子库（含演示数据）。
- 启动时若发现 `app/data/version_plan.db`（或 `_lt`）**缺失或表数为 0**，自动复制种子库回去；**已有数据绝不被覆盖**。
- 随后调用各插件 `ensure_schema()` 幂等补建表，再跑一致性校验。

### 实测覆盖（已在包内副本上跑过）

| 场景 | 结果 |
|---|---|
| 正常解压启动 | 5 插件注册、一致性告警 0、两套导航可见、11 个页面全部 200 |
| 删除两个插件库后启动 | 自动从种子库恢复，17 / 16 张表，200 条需求数据回位，告警 0 |
| 把插件库清成 0 字节后启动 | 同上，自动恢复 |
| 5000/目标端口被占用 | 自动顺延到下一个端口并提示，服务正常 |

### 校验

- 包内文件 693 个，含 `python/python.exe`；无 `__pycache__`、`*.pyc`、`*.db-wal`、`*.db-shm`。
- sha256：`7d89762f1d65a92d656a9324bbb70bc7431589bf59cb7b96f025b4bb977ff53e`

### 升级方式

用本包替换旧目录即可（或解压到全新目录）。旧数据保留在 `app/data/` 与 `app/business.db`，不会被新版覆盖。

## V13.0.0.2 · 关键修复版（Python 3.11 语法兼容）

### 这一版修的是什么（你日志里的那个报错）

```
[插件加载] 跳过 version_plan: f-string expression part cannot include a backslash (trains.py, line 295)
[插件加载] 跳过 version_plan_lt: f-string expression part cannot include a backslash (trains.py, line 295)
```

- **根因**：程序包内置的运行时是 **Python 3.11**。Python 3.11 不允许在 f-string 的 `{...}` 表达式里出现反斜杠（`\'`），只有 3.12 起才放开。插件 `trains.py` 第 295 行构造 SQL 时用了这种写法。
- **为什么表现为"插件不见了 + 满屏尚未建表"**：插件文件导入失败 → 插件被跳过 → 没有注册、没有建表 → 导航里没有这两套插件，管理页按登记表清单去比对空库，于是刷出 29 条告警。这跟 V13.0.0.1 里的"空库"现象是**两个独立成因**，之前只修了后者。
- **修复**：改写该 SQL 拼装逻辑（改成字符串拼接，不再依赖 3.12 特性）；两套插件同步修改。

### 防止复发

- 打包前新增 **Python 3.11 全量语法编译检查**：`python3.11 -m compileall app`，任一文件不通过就不出包。
- 两个插件的独立安装包也用同一检查复验过（包内 `version_plan-13.0.1.2.zip`、`version_plan_lt-13.1.0.1.zip`）。

### 实测（全部在"内置同版本 3.11 + 包内同版本依赖"环境跑）

## v13.0.0.3 — 「版本规划·原版风格」真正还原 Leantime 皮肤

### 这版解决了什么

v13.0.0.2 里两套「版本规划」插件被反馈"看起来一模一样"。核实结论：两套 Python 插件确为同一套代码的克隆（`vp.css` md5 相同、41 条路由相同、16 张表同构、模板仅前缀不同），此前"原版风格"名不副实。

真正的 Leantime 版是 **PHP 插件**（`app/Plugins/VersionPlan`，11 控制器 / 13 模板），只能跑在 Leantime + PHP + MariaDB 里，无法进入 Python 便携包。因此本版按用户选定的方案 A：把 `version_plan_lt` 按 Leantime 原版的**视觉与交互**还原，业务逻辑继续跑 Python。

### 改动明细

1. **新增插件内壳模板**
   - `vpl_shell_top.html`：顶部青色栏（品牌 / 面包屑 / 产品 chip / 账号圆点）+ 内容区横向胶囊导航（驾驶舱 / 产品 / 需求归集 / 需求评估 / 车次日历 / 装车工作台 / 版本规划 / 客户矩阵 / 客户回告）。
   - `vpl_shell_bottom.html`：闭合壳层。
   - 13 个页面模板统一换壳（`vpl_nav.html` → 壳模板）。
2. **Leantime 配色与版式**
   - `static/vp.css` 追加"Leantime 原版风格皮肤"：`--vp-*` 变量改青色系（`--vp-blue:#0f766e`、`--vp-bg:#f2f5f5`），页头包成白色卡片，`.vp-card` 白底圆角 10px + 细边 + 淡阴影，KPI 左侧色条改青 / 琥珀 / 绿 / 紫，按钮圆角 7px、primary 深青，标签圆角胶囊。
   - 装车工作台容量条改为可样式化的 `.vp-capbar`（≥70% 琥珀、≥95% 红）。
3. **门禁行式布局**
   - 版本详情「7 项确认清单」加 `vp-gate-table` 类，表格行改为卡片行（`grid 40px / 1fr / 322px`）：序号青色加粗 + 检查项 + 结论下拉 / 证据 / 保存。
   - 「四方签核」卡片与 KPI 卡同步按原版样式重排，窄屏（≤920px）自动折行。
4. **另一套不受影响**：`version_plan`（版本规划管理）保持原有蓝色风格，平台本体零改动。

## v13.0.0.4 — 版本规划·原版风格插件按 Leantime 1:1 重建

**这不是换皮肤。** v13.0.0.3 只改了颜色和卡片样式，被你否掉之后，本版按 Leantime 原版 PHP 插件的**页面骨架、信息架构、交互流程、界面布局**逐页重建了 `version_plan_lt`（业务与数据仍由 Python 侧承担，插件保持外部可卸载）。

### 二、13 个页面逐个按原版重建

- **驾驶舱**：4 个 KPI（产品 / 需求 / 车次 / 版本）+ 产品表 + 「下一步」提示卡。

- **需求评估**：1:2 两栏——左待评估表（当前分、最近结论），右打分表单（四维滑块 + 结论说明），提交即写评分并自动判定（≥70 规划池 / 40-69 挂起 / <40 不做）。
- **车次日历**：开一个车次（月份 / 容量 / 发车日）+ 琥珀「临时加车（热修复）」按 `H` 后缀编号 + 卡片网格（编号 / 产品·月·发车日 / 状态 / 装载 `load / capacity 人日` / 2px 容量条 ≥80% 琥珀 ≥100% 红 / 停发原因 / 装车工作台 / 恢复发车）；按**月份 chips 筛选**，不再一次铺 30 个车次。

- **版本规划**：「从车次生成版本」表单（车次 / 版本号 / 类型 / 冻结日 / 发布日）+ 版本表（状态 / 容量负载 / 冻结·发布 / 确认与签核）。
- **版本详情（确认与签核）**：4 KPI（容量负载 / 装车需求条数 / 清单 x/7 / 发布门禁）+ 左 7 项硬门禁独立卡片（结果下拉 + 证据 + 保存）+ 右三方（定制版四方）签核卡片（同意 / 驳回 + 意见）+ 发布门禁文案 + 回滚方案 + 发布按钮，最下装车需求表。
- **发布受控（新增页）**：发布门禁一览表（清单 x/7、签核缺口、门禁「可发布」绿 / 「锁定」红）+ 发布记录表。
- **客户回告**：客户表（等级 pill，定制版琥珀）+ 新建客户 + 发回告 + 回告记录；原 `/report` 独立页已收敛进本页（旧地址自动跳转）。
