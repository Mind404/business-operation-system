# 业务高效运转系统 · 插件接入规范 v1.0

> 版本：v1.0 ｜ 适用：v11.0 平台化版本 ｜ 发布：2026-10-21
> 定位：本系统是**信息聚合平台**（"容器"与"调度中心"）。所有业务模块（WBS、需求收集、测试、Bug、版本、文档等）都是**插件**：可独立运行，也可按本规范接入平台，纳入统一权限、统一审批、统一聚合管理。

---

## 1. 核心概念

| 概念 | 说明 |
|---|---|
| **平台** | 本系统核心，只做通用能力：登录、用户与角色、统一审批流、聚合视图、插件接入管理、数据字典、操作日志、全局搜索、个人中心、AI 只读辅助 |
| **插件** | 一个业务模块（如"需求收集"、"测试管理"）。两种形态：**平台内置插件**（代码包放进 plugins/ 目录）或 **外部独立系统**（自己独立运行） |
| **P0 强管控插件** | WBS 计划管理、需求收集。优先级最高、深度设计、严格控流程控变更，其余方向由各团队自行迭代后接入 |
| **接入登记** | 插件/外部系统接入平台的第一步：在「系统管理 → 外部系统接入」登记，平台签发插件标识 |
| **数据字典** | 平台规定的统一字段语义标准（项目/任务/需求/风险/交付物等怎么表达），保证多插件数据可聚合 |

---

## 2. 接入方式（二选一）

### 方式 A：API 对接（推荐）
插件提供 REST API，平台通过接口读取/接收数据。

**认证**：平台向插件签发 `plugin_token`；插件调用平台接口时携带，平台校验。

```
请求头：
  X-Plugin-Id: testing
  X-Plugin-Token: <平台签发>
```

### 方式 B：数据库直连（只读聚合）
插件数据库与平台网络互通，平台以**只读**方式读取插件库，做聚合分类与展示。
> 平台只读外部数据；**绝不反向写插件业务库**。插件数据修改由插件自身完成。

---

## 3. 数据上报与数据字典（信息打通的关键）

插件接入后需向平台上报数据，平台存入 `external_data_cache` 聚合缓存，供聚合视图统一展示。

### 3.1 上报接口
```
POST /api/external/report
参数：system_id, category, payload(JSON)
```
外部插件按分类上报数据快照；平台展示"聚合缓存"，不替代插件自身深度功能。

### 3.2 统一数据字典（字段语义标准）

| 分类 category | 建议字段 | 含义 |
|---|---|---|
| project 项目 | id, name, owner, status, start_date, end_date | 项目/计划 |
| task 任务 | id, project_id, name, owner, plan_start, plan_end, status, progress | 任务/节点 |
| requirement 需求 | id, code, title, source, priority, status, delivery_date | 需求条目 |
| risk 风险 | id, title, level, status, owner, due_date | 风险池 |
| deliverable 交付物 | id, name, task_id, owner, status, due_date | 交付物 |

> 插件业务字段可以更丰富；接入时**必须**把核心字段映射到上表口径，平台才能做跨插件聚合。字段自动映射建议由平台内置小模型辅助生成（见 §8）。

### 3.3 同步频率
- 重要数据（状态、进度、交付日期）：实时或每小时上报一次
- 常规数据：每天定时上报一次

## 4. 审批统一（"审批后生效"一律走平台）

插件内任何"审批后生效"的操作（状态变更、发布、关闭等），**不得**在插件内自行生效，必须调用平台统一审批服务：

```
POST /api/approval/submit
参数：plugin_id, record_type, record_id, action, payload
```
- 平台按该插件/记录类型配置的**审批流**逐级审批（可在「审批流配置」中配置多级步骤）
- 审批通过后由平台回调落地（或插件轮询审批结果后自行落地）

**审批流配置**（管理员在「系统管理 → 审批流配置」）：
- 每个插件 + 记录类型可配置一条审批流
- 步骤可多级（如：第1级 管理员 → 第2级 管理员）
- 未配置时默认单级管理员审批

---

## 5. 权限与角色

- 接入平台后，平台为插件**统一分配权限与角色**（哪些用户/角色可用该插件）
- 插件内部可保留自己的细粒度权限（业务执行权）
- 平台账号体系唯一：用户由「用户管理」创建，角色分 `admin`（管理员）/ `user`（普通用户）

---

## 6. 菜单与入口

| 形态 | 入口方式 |
|---|---|
| 内置插件 | 插件包 manifest 声明 `nav_path`/`endpoint`，自动出现在左侧导航 |
| 外部系统 | 接入登记时填写访问地址，聚合视图/接入管理中提供跳转入口 |

## 7. 接入验收清单（接入测试）

管理员在「外部系统接入」点「测试」验证登记信息；正式接入需满足：

- [ ] 已登记（名称、插件标识、接入方式、连接配置齐全）
- [ ] 核心字段已按数据字典映射（有映射说明）
- [ ] "审批后生效"操作已接入平台审批流（有审批流配置）
- [ ] 数据已按 §3 上报，聚合缓存有数据
- [ ] 权限已由平台分配（用户/角色可用性确认）

---

## 8. 内置小模型（AI 只读辅助）

平台内置本地小模型（千问 2B/4B，Ollama 本地部署，数据不出内网），能力边界：

| 能力 | 说明 |
|---|---|
| 持续监测 | 监测多插件数据库数据变化（任务逾期、需求临期、异常停滞）并预警 |
| 数据智能映射 | 自动识别外部系统字段含义，生成数据字典适配建议 |
| 智能问答 | 回答"某项目当前进度""XX任务阻塞原因"等（标注信息来源与数据时间） |
| 聚合摘要 | 每天自动生成项目状态摘要 |

**AI 边界（硬约束）**：
- AI 是"秘书/翻译官"，**不是决策者**
- **只读分析，绝不写库**，不得直接修改 WBS/需求核心数据
- 所有 AI 建议操作需人工确认
- 问答结果标注信息来源与数据时间
- 本地部署，不依赖公网大模型 API

---

## 9. 示例：接入一个"测试管理"外部系统

1. 管理员在「外部系统接入」登记：名称=测试管理系统、插件标识=testing、接入方式=API、连接配置=接口地址
2. 平台签发 testing 的 token
3. 测试系统按数据字典 category=task/requirement 上报数据（接口地址见 §3）
4. 管理员在「审批流配置」为 testing/record 配置审批流
5. 测试系统内"审批后生效"操作调用平台审批接口
6. 聚合视图中看到测试系统数据 + 预警；AI 可基于其数据问答/摘要
