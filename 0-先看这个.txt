◆ v13.0.0.34 说明（2026-11-19）· 「数据备份」把附件文件一起带走：换机/新装不再需要手工复制 uploads

一、为什么改
上一版验证发现：备份只含数据库和插件包，任务附件等上传文件不在备份里。迁移到新装环境后，
任务还在、附件点开却提示文件不存在——这违背了「备份就是为了便捷、规范地做数据迁移」的目标。

二、现在的备份范围（一套备份 = 同一时间戳的一组文件）
- 主库 business.db；
- 各插件独立库（app/data/*.db）；
- 插件包快照 pluginpack_备份_<ts>.zip；
- 新增：附件文件包 files_备份_<ts>.zip，收 app/plugins/*/uploads/ 下的任务附件、
  导入快照、快照回收站等全部上传文件（顶层 app/uploads 若存在也收）。
- 文件没有变化时不再重复打包，沿用上一份附件包，避免每次启动都复制一份；
- 附件有变化、而数据库没变化时，会强制重新生成一套完整的新备份组，不会出现“只有附件包、
  没有主库”的残缺组；每个组都保留最近 7 份。

三、恢复行为
- 「整组恢复」：按「插件库 → 主库」恢复数据库，然后补回同组附件包里的文件；
- 附件只补缺失、不覆盖已存在的文件（避免用旧备份把线上正在用的附件退回旧版本）；
- 单库「整库覆盖」主库时，也会补回同组附件；
- 备份列表里附件包单独显示为「附件文件」，也可以只对它点「还原附件文件」；
- 恢复到新装环境后，账号、项目、任务、插件数据、附件文件都已就位，附件可直接下载。

四、旧备份的边界（无法补救，只能手工处理）
v13.0.0.33 及更早版本生成的备份里没有附件包，那批备份恢复后仍需手工复制
app/plugins/*/uploads/；或者直接用「保留数据目录、只换程序」的升级方式。

五、本轮验证
- 附件迁移专项 16/16：备份组含附件包、打包内容正确、文件未变化不重复打包、新增文件后
  生成完整新组、新装环境只靠备份组恢复后附件可直接下载、单独还原只补缺失不覆盖。
- 全量 API 回归 142/142；备份恢复专项 10/10；v13.0.0.11 → 当前版本专项 17/17
  （v11 旧备份无附件包，按上文边界处理）。

◆ v13.0.0.32 修正（2026-11-19）· 从 v13.0.0.11 升级后的数据备份/恢复验证：修掉两处“恢复就把人踢下线”

1. v11 启动、admin 登录、建项目/任务、v11 手写备份：正常，v11 备份文件里确实有那 2 条任务。
2. 换成当前版本启动后 healthz 报 13.0.0.32；admin 仍能登录；原项目与 2 条任务完整；备份页能列出 v11 时期的备份。

1）「只有一个 admin、但已经有业务数据」的老库，恢复数据时被当成“刚装好的空库”
   原判断只看账号数（≤2 且只有 admin/product）。上面这个升级库正好只有 1 个 admin，于是从备份恢复数据时
   把备份里的账号一并搬回来并清会话，人直接被踢到登录页——与“只恢复数据不踢人”矛盾。
   改法：新增 _db_looks_fresh()，账号条件之外再看业务表是否为空（跳过 user/session/log/配置类表，
   任一业务表有行就不算新装）。单库恢复与整组恢复两处判断都换成了它。
   真正的新装（空库 + 只有一个 admin）仍然会把备份里的账号导入并要求重登，这条路径单独做了验证（3 项全过）。

2）整组恢复（一次恢复一整套备份）无条件踢登录
   整组恢复走的也是“只恢复数据”，user_sessions 明确在跳过清单里，登录态本不该失效；
   但结束时不管是不是新装都 session.clear() + 跳登录页。改法：只有确实属于“新装导入账号”时才清会话、要求重登；
   其余情况保留当前会话，提示“账号与会话未改动，无需重新登录”，回到备份页。

- v13.0.0.28 备份恢复专项：10/10 通过（默认 data 不踢人、full 强制重登、恢复后完整性自检）。
- 升级链路专项：16/16；新装导入账号专项：3/3。
- 服务日志无 traceback、无 500。

五、升级方式（照旧）
停服 → 备份整个目录 → 用新包覆盖程序文件（business.db、data、backups、uploads 保留不动）→ 启动。
老备份不用先转格式：恢复时选“只恢复数据”，表结构/账号/插件登记/模型配置都保持当前版本。

◆ v13.0.0.31 修正（2026-11-19）· 全量虚拟数据回归：修掉列表/详情页的逐行查库

一、发现的问题（全量回归时暴露）
- 任务列表、项目详情、到期预警这几处，每渲染一行任务都要单独查一次 users 表来把登录名换成显示名。

- 到期预警、清单类页面走同一套解析，一并变快。

◆ v13.0.0.30 修正（2026-11-19）· 父任务进度条改为自动汇总

一、原来的问题
- 父任务那一行和普通任务长得一样，都挂着可拖的进度条，于是容易出现「子任务都做完了，父任务进度条还停在 0」；
- 手动拖父任务的进度和子任务实际进度对不上，页面上看着互相矛盾。

二、现在的规则（v13.0.0.30 起）
- 有子任务的行：进度条变成只读的自动汇总条（蓝色填充 + 百分比），数值 = 直接子任务进度均值，父任务已完成时固定 100%；
  鼠标悬停会提示「父任务进度由子任务自动汇总（子任务进度均值），不需要手动拖」。
- 没有子任务的行：仍然是可以拖动的进度条，正常手填。
- 只读和可拖是当场判断的，不靠事先标记：新建一个空任务时可拖；给它加了子任务，下次刷新/保存后自动变只读；
  子任务删光后，这一行自动恢复成可拖。
- 新增子任务、删除子任务、改子任务状态或进度，父任务行的自动条都会立即跟着变，不需要刷新页面。

三、需要注意
- 父任务的状态与进度都由子任务决定，手动改父任务只是当场生效，下次打开会被算回（v13.0.0.29 起就是这个口径）。
- 父任务进度取的是「直接子任务」的均值，不是所有层级拉平后的加权值；层级越深，父任务看的是它下面那一层。

◆ v13.0.0.29 修正（2026-11-19）· 父任务状态/进度与子任务真正联动

一、原来的问题
- 只有"改子任务状态"这一个动作会触发上卷，"拖进度条"不触发；
- 上卷规则只升不降：子任务从全部完成退回未开始/进行中时，父任务仍卡在「已完成」；
- 父任务进度从来不由子任务算，于是出现「父任务已完成 100%，子任务还有未开始的」这种画面；
- 子任务自己也能自相矛盾：状态「未开始」但进度 30%（截图里的 1.3 就是），或者「已完成」但进度 60%。

二、现在的规则（v13.0.0.29 起）
- 父任务状态按直接子任务全量推导，可升可降：
    子任务全部已完成 → 父已完成；有子任务阻塞 → 父阻塞；全部未开始 → 父未开始；其余 → 父进行中。
  已取消的子任务不参与推导。
- 父任务进度 = 直接子任务的进度均值（父已完成时固定 100）。
- 状态与进度双向联动：进度拖到 100% 自动转「已完成」；0–100 之间有进度时「未开始」自动转「进行中」；
  状态改成「已完成」进度补到 100，「未开始」进度归零。
- 打开项目详情页时会做一次对账：父任务与子任务的矛盾值就地纠正（含上述「未开始 30%」这类历史行），
  数据本就一致时零写入、不产生日志。
- 行内改完状态/进度，页面上的父任务行会立即跟着变，不需要刷新。

三、需要注意
- 父任务的状态与进度现在完全由子任务决定。手动改父任务的状态/进度只是当场生效，下次打开详情页
  （或任一子任务变动）会被按子任务重新算回来。阶段级想表达"整体被外部阻塞"，请把阻塞落到具体子任务上。

◆ v13.0.0.28 修正（2026-11-19）· 日常恢复默认「只恢复数据」；备份不再漏掉刚改的数据

一、恢复的默认方式改为「只恢复数据」
- 「只恢复数据」（data）：只把业务数据搬回备份时点，当前版本的表结构、账号密码、
  插件登记、模型配置、在线会话都不动，恢复完没人被踢下线。日常恢复一律走这个。
- 「整库覆盖」（full）：会把库结构、账号、会话一起退回备份时刻，只用于整库回退 /
  换机救火。必须显式点「整库覆盖」才会执行；接口层不带 mode 也按 data 处理，
  脚本或旧表单误调用不会触发整库回退。
- 整组恢复本来就是只搬业务数据，页面确认文案里原来写着"恢复完成后需要用备份里的
  账号重新登录"，与实际行为不符，已改正（不会踢人）。

二、备份不再漏掉刚提交的数据（真实缺陷）
- 旧实现先做 wal_checkpoint(TRUNCATE) 再直接复制 .db 文件。活动连接占着 WAL 时
  checkpoint 返回 busy，代码没看返回值，于是复制出来的 .db 缺少最近提交、仍在
  -wal 里的记录；而"内容相同就不重复备份"的判重也是对这个旧文件算 sha256，
  结果是：刚改的数据永远进不了新备份，系统还认为没必要再备一次。
- 现在改用 SQLite 在线备份 API 直接取一致快照（已提交数据一定包含），
  再对快照做判重与落盘，快照失败才退回文件复制并打日志。

◆ v13.0.0.27 修正（2026-11-19）· 恢复后强制重登；刷新不再重复跳转；备份目录不再产生垃圾文件

一、整库恢复后，所有人统一重新登录
- 之前只在「当前登录的 token 恰好不在备份里」时才跳登录页，其他人可能带着旧身份继续用，
  出现"数据回退了、人还是原来那个会话"的错位。
- 现在主库整库恢复成功后：清空在线会话表 → 会话世代号 +1 → 当前页面跳登录页并提示
  「系统数据已被管理员恢复，所有登录状态已统一失效，请重新登录」。
  任何旧 cookie 下一次请求都会被拦到登录页，不会再被"自动认领"成新会话。
- 只恢复数据（mode=data）不受影响：账号、会话、结构都不动，不会把谁踢下线。

二、页面定位参数用完即摘，刷新不再重复跳转
- 从"到期预警/待办/新建任务"跳进 WBS 详情时，地址栏带 ?task_highlight=<任务id>，
  页面会滚到目标行并闪烁高亮。以前这个参数一直留在地址栏，用户按 F5 刷新会再跳一次、
  再闪一次，看起来像"刷新后自己跑了"。
- 现在跳转定位与高亮照旧（首次进入仍然定位到那一行），但参数在定位后立即从地址栏摘掉，
  刷新就停在当前位置，不再二次跳转、不再闪烁。

三、备份目录不再产生 .db-shm / .db-wal 垃圾文件
- 恢复时以只读方式打开备份文件，SQLite 会在备份旁边生成 -shm/-wal 附属文件；
  这些文件既没用，按文件名排序时还会被排到 .db 后面（脚本/人工挑选备份时容易选中它们）。
- 现在备份一律以 immutable 只读方式打开，不再生成任何附属文件。

- 现象：点「恢复」后有几秒钟全站 500，控制台报
  database disk image is malformed / disk I/O error，连登录页都打不开。
- 原因：整库在线覆盖后，残留的 WAL/共享内存页与旧连接不一致，第一批新连接建库时报错。
- 修复：
  1) 恢复后强制合并 WAL（checkpoint + journal_mode 切到 DELETE 再切回 WAL），
     由 SQLite 自己清掉残留帧，不再手工删 -wal/-shm（手工删反而会引发 disk I/O error）。
  2) 覆盖完成后立刻做 PRAGMA integrity_check；不通过就用「恢复前保护」备份自动回滚，
     并提示「本次恢复未生效、数据完好」，绝不把坏库留给用户。
  3) 开闸前先预热连接（最多 2 秒），确认库能正常读写再放请求进来。
  4) 建库连接遇到瞬时 disk I/O error 自动重试（最多 8 次 / 2 秒），不再直接 500。
- 验证：恢复后立即登录 200、工作台 200、integrity_check=ok；恢复过程中 10 并发读 0 个 500。

二、Excel 列数不足时导入报 500（P1）
- 现象：上传只有「WBS编号 / 阶段·任务」两列的 Excel，服务端 IndexError，整页 500。
- 原因：解析器直接按下标取「工作内容 / 负责人 / 日期 / 交付物」，行比 8 列短就越界。
- 修复：所有列改为安全取值（缺列按空处理）；整行不足 3 列时给出明确提示
  「第 N 行：只有 X 列，列数不足，请先下载最新模板（11 列）再填写」，而不是崩掉。
  5 列、9 列等"能用但缺列"的文件仍可正常导入，缺的字段留空。

问题根因：
  公司内网 EDR（终端安全软件）会在浏览器进程内拦截超过 ~6.26MB 的 JS 文件，
  自动净化/篡改内容导致「Unexpected token '{'」语法错误，表格白屏。
  原 Univer 表格引擎是单个 6.8MB 的 JS 文件，每次加载都被 EDR 拦截。

本版本根治方案：
  将 6.8MB 单文件引擎重新构建为 7 个独立 chunk（ES Module 分包）：
    · engine.js（入口）：仅 1.1KB（EDR 不扫小文件）
    · univer-engine-render：4.37MB（< EDR 阈值 6.26MB）
    · univer-docs：2.68MB
    · univer-sheets：1.33MB
    · univer-engine-formula：1.12MB
    · univer-sheets-extras：0.60MB
    · univer-core：0.49MB
  每个 chunk 都远低于 EDR 大小阈值，加载时不会被拦截。

使用方式：
  · 直接双击「start.bat」即可（HTTP 模式，无需装证书）
  · 不再需要「start-https.bat」和「install-cert.bat」
  · 表格功能：新建/编辑/保存/筛选/导出 Excel 全部保持可用

  · 首次打开表格时需加载 7 个文件，比单文件稍慢（约 1-2 秒），属正常现象
  · 如仍有问题，请按 F12 打开浏览器控制台，把红色错误截图发开发人员
